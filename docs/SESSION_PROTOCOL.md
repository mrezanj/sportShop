# SESSION PROTOCOL — شروع، Checkpoint و انتقال گفت‌وگو

## هدف
انتقال کار بین چند گفت‌وگو بدون نیازسنجی مجدد، گم‌شدن تصمیمات یا دوباره‌کاری.

## A. شروع گفت‌وگوی جدید
پرامپت شروع:

> طبق `docs/AI_WORKFLOW.md` عمل کن. ابتدا آخرین وضعیت Repository و اسناد را بررسی کن. سپس `HANDOVER.md` و `PROJECT_TRACKER.md` را با کد واقعی تطبیق بده. نیازمندی‌های مصوب را از `PROJECT_MASTER.md` بخوان و از من نخواه دوباره آن‌ها را توضیح بدهم. فعلاً فقط وضعیت واقعی، مغایرت‌ها، کار بعدی و فایل‌هایی را که برای ادامه لازم‌اند گزارش کن. پس از آن کار مرحله جاری را ادامه بده.

## B. زمان‌های اجباری Checkpoint
Checkpoint باید در این زمان‌ها پیشنهاد/تهیه شود:
- پایان هر زیرمرحله قابل تحویل؛
- پس از تصمیم معماری یا تغییر Scope؛
- پیش از شروع کار پرریسک یا Migration بزرگ؛
- وقتی گفت‌وگو طولانی شده یا احتمال انتقال به گفت‌وگوی جدید هست؛
- به درخواست کاربر.

به حد دقیق محدودیت گفت‌وگو وابسته نباش؛ زمان آن قابل تضمین یا مشاهده دقیق نیست.

## C. قالب Checkpoint
1. تاریخ و شاخه/Commit مبنا (اگر معلوم است)
2. هدف مرحله
3. کارهای تکمیل‌شده با شواهد
4. کارهای نیمه‌تمام
5. فایل‌های کد تغییرکرده
6. Migration و دستورات اجراشده
7. تست‌ها و نتایج واقعی
8. خطاها و ریسک‌ها
9. تصمیمات جدید و وضعیت تأیید
10. نیازمندی‌های Tracker که تغییر وضعیت می‌دهند
11. فایل‌های مستنداتی نیازمند تغییر
12. متن کامل نسخه جایگزین هر سند تغییرکرده
13. دستور آماده گفت‌وگوی بعدی

## D. قوانین به‌روزرسانی اسناد
- فقط سندهایی را تغییر بده که واقعاً تحت تأثیر قرار گرفته‌اند.
- محتوای کامل سند را ارائه کن تا کاربر بتواند جایگزین کند.
- اگر سند هنوز داده قطعی ندارد، `UNKNOWN` یا `TO_BE_VERIFIED` ثبت کن؛ حدس نزن.
- Tracker باید وضعیت Backend، Frontend، Tests و Acceptance را جدا کند.
- تصمیم پیشنهادی را با تصمیم تأییدشده مخلوط نکن.
- هر سند به‌روزشده باید با بقیه اسناد سازگار باشد.
- در صورت عدم امکان دسترسی مستقیم به GitHub، فقط متن Paste-ready بده.

## E. پرامپت انتقال به گفت‌وگوی بعدی
در پایان هر Checkpoint یک متن کوتاه و مستقل تولید کن که:
- Repository و شاخه را مشخص کند؛
- اسناد لازم برای مطالعه را نام ببرد؛
- آخرین وضعیت و Commit مبنا را ذکر کند؛
- هدف دقیق بعدی را مشخص کند؛
- فایل‌های موردنیاز را فهرست کند؛
- از تکرار نیازسنجی جلوگیری کند؛
- از مدل بخواهد ابتدا وضعیت واقعی را بررسی کند.

## F. پایان کار
کاربر باید:
1. متن کامل اسناد را در مسیرهای اعلام‌شده جایگزین کند.
2. فایل‌های جدید را اضافه کند.
3. تغییرات را بازبینی کند.
4. Commit و Push کند.
5. در گفت‌وگوی بعدی Repository را دوباره بررسی کند.

هیچ‌گاه ادعا نکن فایل‌ها در GitHub ذخیره شده‌اند مگر ابزار واقعاً این عملیات را انجام داده و موفقیت آن را گزارش کرده باشد.
